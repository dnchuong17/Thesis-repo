This chapter explains how the VietFlood prototype was implemented. The work includes the backend services, mobile application, web dashboard, shared library, deployment process, and user management. The main goal was to make a working prototype that can receive flood reports from citizens, store them in the backend, and allow administrators or relief users to view the information.

The system is separated into four parts. The backend uses NestJS and contains the API gateway, authentication service, reports service, message queues, cache, media upload, and live tracking gateway. The mobile app supports citizen reporting and relief viewing. The web dashboard supports administrator review. The shared package keeps common code such as logging, Redis, and Cloudinary helpers.

\section{Technique and Tools}

VietFlood was built as a multi-platform system. The backend uses NestJS and TypeScript \cite{nestjsDocs,typescriptDocs}. The mobile app uses Expo React Native \cite{expoDocs,reactNativeDocs}. The web dashboard uses Next.js \cite{nextjsDocs}. These tools were chosen because they all work well with TypeScript, but each platform can still be developed and deployed separately.

\noindent\textbf{a) Version Control and Build Tools:} The source code is managed with Git. The backend is arranged as a NestJS workspace with the API gateway, auth service, and reports service. Each backend app has a Dockerfile. Docker Compose starts the backend services with RabbitMQ and Redis for local development \cite{dockerComposeDocs}. For deployment, Docker images are built and run on Azure App Service \cite{azureAppServiceContainersDocs}.

\noindent\textbf{b) Front-end Development:} The mobile app uses Expo, React Native, TypeScript, React Navigation, Redux Toolkit, SecureStore, image picker, and device location \cite{expoDocs,reactNativeDocs,typescriptDocs,reduxToolkitDocs}. These tools support login, profile, report creation, evidence upload, and relief report viewing. The web dashboard uses Next.js, React, TypeScript, and Tailwind CSS \cite{nextjsDocs,reactDocs,typescriptDocs,tailwindDocs}. It allows administrators to filter reports, preview evidence, and update report status.

\noindent\textbf{c) Back-end Development:} The backend follows a microservice style with NestJS microservice support \cite{nestjsMicroservicesDocs}. The API gateway exposes REST endpoints and Socket.IO events \cite{socketioDocs}. The auth service handles registration, login, refresh tokens, profile data, logout, and user administration. The reports service handles report creation, report reading, report update, report deletion, evidence metadata, and cache refresh.

\noindent\textbf{d) Database and Media Storage:} PostgreSQL stores users, refresh tokens, and reports. TypeORM maps database tables to service entities \cite{typeormDocs}. Redis stores report cache records \cite{redisDocs}. Cloudinary stores evidence files \cite{cloudinaryUploadDocs}. The database stores only media metadata, such as URL, public ID, and resource type. JSONB is used for flexible evidence data \cite{postgresqlJsonDocs}.

\noindent\textbf{e) Cloud Service and Runtime Configuration:} The deployed backend runs on Azure App Service. Secrets are not written in the source code. Database URL, Redis settings, RabbitMQ credentials, JWT secrets, refresh-token secret, Cloudinary credentials, and admin seed values are passed through environment variables.

\section{Messaging Broker Implementation}

RabbitMQ is used between the API gateway and the internal backend services \cite{rabbitmqConfirmsDocs,nestjsMicroservicesDocs}. The gateway receives HTTP requests from the mobile app or web dashboard. Then it sends a message to the service that owns the business logic. The auth service listens on \texttt{auth\_queue}. The reports service listens on \texttt{reports\_queue}.

The gateway does not directly run authentication or report logic. It sends message patterns for registration, sign in, profile loading, refresh, logout, report creation, report listing, update, and delete. This makes the gateway a transport layer, while each service keeps its own data rules.

Gateway calls use timeout and retry rules. Upload requests are given more time because they may upload files to Cloudinary. Small requests use shorter limits. If a service fails, the gateway returns a controlled HTTP response instead of making the client wait too long.

\section{Authentication and Authorization Implementation}

VietFlood uses username and password login. Passwords are hashed with bcrypt before saving \cite{provos1999bcrypt}. After login, the auth service creates an access token and a refresh token. The access token uses the JSON Web Token format \cite{jones2015jwt}. It stores the user ID, username, role, first name, and last name. The gateway uses this data for protected routes.

\subsection{Authentication Mechanism Implementation}

\noindent\textbf{a) Registration Process}

Registration is handled by the auth service. The service checks if the email, username, or phone number is already used. If one of them exists, the request is rejected. If the data is valid, the password is hashed with bcrypt and the new user is saved in the \texttt{users} table. The backend returns only a small success response, not the password hash.

\noindent\textbf{b) Login Process}

Login uses the \texttt{/auth/sign\_in} endpoint. The auth service finds the user by username and compares the password with the stored bcrypt hash. If the password is correct, it returns an access token and a refresh token. On mobile, users can choose saved login or session-only login. On the web dashboard, the app loads the current profile before showing admin pages.

\subsection{Refresh Token Implementation}

Refresh tokens are stored as hashed values in the \texttt{refresh\_tokens} table. Each token belongs to one user and has expiration and revocation data. When a user signs in again, the service can update the existing token row instead of creating too many active tokens.

The refresh endpoint lets the mobile app and web dashboard request a new access token without logging in again. On mobile, the token helper keeps the same storage choice as login. If the user selected saved login, the new token is stored in SecureStore. If the user selected session-only login, the token stays in memory.

\subsection{Authorization Process Implementation}

Authorization is checked at the API gateway. JWT guards validate the token. Role guards check if the route is allowed for a citizen, relief user, or administrator. Citizens can create and manage their own reports. Relief users can read reports and view locations. Administrators can review evidence, update report status, and manage users.

This role separation is important. Relief users do not verify or reject reports in the current prototype. Verification, rejection, and resolution stay as administrator actions.

\section{Report Processing and Evidence Upload Implementation}

Report creation starts in the mobile app. A citizen fills in category, description, address, coordinates, urgency, severity, and optional evidence images. The app sends the data as multipart form data, so text fields and image files are sent in one request.

The API gateway receives the files and uploads them to Cloudinary \cite{cloudinaryUploadDocs}. After that, it sends the report payload and evidence metadata to the reports service through RabbitMQ. The reports service saves the report in PostgreSQL. Category values are stored as arrays, and evidence is stored as JSONB with URL, public ID, and resource type \cite{postgresqlJsonDocs}. After saving, the service writes a Redis cache entry \cite{redisDocs}.

\subsection{Report Update and Delete Implementation}

Report update uses the same upload path as report creation. If a citizen adds new evidence, the gateway uploads the new files to Cloudinary. The reports service checks report ownership, merges new evidence with old evidence, updates image URLs, deletes the old Redis cache entry, and writes a new cache entry.

Report deletion also checks ownership. The reports service reads Cloudinary public IDs from the stored evidence metadata and deletes the media when it exists. Then it deletes the report row from PostgreSQL and removes the Redis cache key.

\section{Public Library Implementation}

The shared backend package is named \texttt{vietflood\_common}. It contains reusable services for logging, Redis, and Cloudinary. This package helps the gateway, auth service, and reports service avoid repeating the same infrastructure code.

The Cloudinary helper supports buffer upload, file-path upload, base64 upload, single delete, bulk delete, rename, optimized image URL generation, and raw URL generation. In the report workflow, the gateway uses buffer upload for evidence files. The reports service uses bulk delete when a report is removed.

The Redis helper wraps common operations such as \texttt{set}, \texttt{get}, \texttt{del}, and \texttt{publish} \cite{redisDocs}. The logger service adds service names and request context to logs. This makes backend behavior easier to trace when many services run together.

\section{Real-Time Tracking Implementation}

VietFlood includes a Socket.IO gateway for live location sharing \cite{socketioDocs}. The client sends latitude, longitude, accuracy, heading, speed, and timestamp. The gateway checks latitude and longitude before broadcasting. Invalid coordinates return an error to the sender. Valid coordinates are sent to connected clients.

The gateway also handles connection and disconnection events. When a client disconnects, other clients can be informed. This feature is useful for relief work because a relief screen can receive a user's latest location. In this prototype, the feature proves the live communication path. Authenticated sockets and stored location history can be added later.

\section{Mobile Citizen Feature Implementation}

\subsection{Report List and Profile Access}

The mobile app provides the main citizen workflow after login. It loads the user profile through an authenticated endpoint. It also loads reports through the report service wrapper. The wrapper normalizes backend data because some fields may use different names between backend and client models.

The citizen report list shows submitted reports with status, category, location, and evidence information. Status labels are normalized before display. This makes the interface more stable while the prototype is still changing.

\subsection{Create Report Implementation}

The create-report screen collects category, description, address, latitude, longitude, urgency, severity, and evidence images. Province and ward selection uses data from the Vietnam Provinces Open API \cite{vietnamProvincesOpenApi}. If the user allows location permission, the app can fill coordinate values from the device.

\section{Relief Feature Implementation}

The relief side of the mobile app is used for reading and locating flood reports. The relief report list shows submitted cases. The detail view shows description, category, address, evidence, and current status. The map screen helps relief users understand report locations.

The relief role is narrower than the administrator role. Relief users can view reports and map information, but they cannot verify, reject, or resolve reports. This keeps report approval under administrator control.

\section{Web Dashboard Implementation}

The web dashboard is the administrator workspace. It starts with admin login, stores the returned tokens, and loads the current profile before showing protected pages. The dashboard loads report records from the backend, formats dates, translates category and status values, extracts evidence thumbnails, and shows reporter information when available.

The dashboard has search and status filtering. Search can match reporter name, account name, phone number, location, and description. Status filtering supports pending, verified, resolved, and rejected states. Status controls call the admin report update route through the API gateway.

\subsection{Evidence Review and Status Update}

Evidence review uses the Cloudinary URLs stored with the report. The dashboard first checks the evidence list and then falls back to the image list. This makes the dashboard work with reports created by different client versions. When the administrator changes report status, the dashboard sends the update to the gateway, and the gateway forwards it to the reports service through RabbitMQ.

\section{Deployment Implementation}

Backend deployment uses Docker images and Azure App Service \cite{azureAppServiceContainersDocs}. In local development, Docker Compose builds the API gateway, auth service, and reports service from source. It also starts RabbitMQ and Redis \cite{dockerComposeDocs}. In production, the same services are pulled as Docker Hub images.

The GitHub Actions workflow builds images for the gateway, auth service, and reports service \cite{githubActionsDocs}. After the images are pushed to Docker Hub, the workflow configures Azure App Service with the Compose file and restarts the application. This makes deployment more repeatable and follows common continuous delivery practice \cite{humble2010continuousDelivery,kim2016devopsHandbook}.

\section{User Management Implementation}

User management is implemented in the auth service and exposed through the API gateway. The service can list users, load one user by ID, update a profile, update a user by ID, and delete a user. All roles use the same user table. The role value can be citizen, relief, or administrator.

The web dashboard validates the profile before showing admin-only screens. Mobile profile screens use authenticated profile and update endpoints so users can update their own information. The role model is simple in this prototype: roles are stored in the database, and route access is checked by guards in the gateway.
