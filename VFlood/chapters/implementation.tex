This chapter describes the implementation of the VietFlood prototype and the concrete outputs produced by the project. The system was implemented to support a complete reporting loop: users authenticate, citizens submit a report with location and optional evidence, the backend stores and serves that report through a stable API, and administrators review and update report status.

The implementation is delivered as four main artifacts: (1) a backend composed of an API gateway, an authentication service, and a reports service; (2) a mobile application for citizen and relief users; (3) a web dashboard for administrators; and (4) a shared library, \texttt{vietflood\_common}, that provides reusable infrastructure across services.

\section{Prototype Deliverables and Technology Stack}

TypeScript is used across the backend and both client applications to keep models, validation rules, and data contracts consistent during development. The backend services are built with NestJS \cite{nestjsDocs} and use NestJS microservice support to communicate through a message broker \cite{nestjsMicroservicesDocs}. The mobile application is built with Expo React Native \cite{expoDocs,reactNativeDocs}, and the web dashboard is built with Next.js \cite{nextjsDocs}.

The prototype is designed to run as containers. Docker Compose is used for local development to start the gateway, services, RabbitMQ, and Redis in a repeatable environment \cite{dockerComposeDocs}. For deployment, container images are deployed to Azure App Service \cite{azureAppServiceContainersDocs}, and build/deploy automation is handled through GitHub Actions \cite{githubActionsDocs}. Sensitive values (database URL, JWT secrets, Cloudinary credentials, broker credentials) are provided through environment variables rather than stored in source code.

\section{Backend Implementation}

\subsection{Service Responsibilities and Routing}

The API gateway is the only backend component exposed to clients. It receives HTTP requests (including multipart uploads), validates access using guards, and forwards internal work to the authentication or reports service. Internal communication uses RabbitMQ request--response message patterns \cite{rabbitmqConfirmsDocs,nestjsMicroservicesDocs}. This layout keeps transport and access control in one place, while moving business logic and database operations into dedicated services.

\subsection{Authentication, Tokens, and Role Checks}

VietFlood uses password-based authentication. Passwords are hashed with bcrypt before storage \cite{provos1999bcrypt}. After login, the authentication service issues an access token and refresh token. Access tokens are JSON Web Tokens that carry identity and role claims needed by the gateway authorization guards \cite{jones2015jwt}. Refresh tokens are stored and rotated to support longer-lived sessions while limiting the impact of token leakage.

The prototype supports three roles: \texttt{citizen}, \texttt{relief}, and \texttt{admin}. Role checks are enforced at the gateway for protected endpoints and admin-only routes. This is a simple model, but it is sufficient to demonstrate the different responsibilities: citizens submit reports, relief users browse and monitor, and administrators review and change status.

\subsection{Report Handling and Evidence Pipeline}

Flood reports are created from the mobile client and received by the gateway as multipart form data. When evidence images are present, the gateway uploads files to Cloudinary and produces a metadata list (delivery URL, public ID, and resource type) \cite{cloudinaryUploadDocs}. The final payload is then sent to the reports service through RabbitMQ. The reports service validates the payload, persists the report using TypeORM \cite{typeormDocs}, and writes a cache entry in Redis for faster follow-up lookups \cite{redisDocs}.

This evidence-first pipeline keeps the database focused on structured report fields while still making evidence available for review. It also makes the report record self-contained: administrators can review a report by reading one database row plus its evidence metadata, without needing local file storage.

Update and delete operations follow the same service boundary. The gateway enforces role permissions, then forwards update/delete commands to the reports service. When a report changes, the reports service invalidates and refreshes cache entries so that subsequent reads reflect the current state.

\subsection{Shared Infrastructure Utilities}

To keep services small and consistent, VietFlood includes a shared library, \texttt{vietflood\_common}, that exposes a logging module and small wrappers for Redis and Cloudinary. Centralizing these utilities reduces duplicated code and makes it easier to apply consistent error handling and configuration across services.

\subsection{Live Location Event Channel}

The prototype includes a Socket.IO gateway used for live location broadcasting \cite{socketioDocs}. Clients emit \texttt{send-location} events with latitude and longitude values. The gateway validates coordinate ranges and rebroadcasts valid updates to other connected clients using a \texttt{receive-location} event. Invalid payloads result in a \texttt{location-error} response to the sender. This feature demonstrates real-time event flow and can be extended with authenticated identities and persistence if needed for operational use.

\section{Client-Side Implementation}

\subsection{Mobile Application Features}

The mobile application is the field-facing interface and is designed for quick submission and reading. After sign-in, the app loads the current profile and displays a report list for the user. Citizens can create a report by providing a category, short description, administrative address fields, and coordinates. Evidence images are selected from the device and uploaded as part of the create report request.

The relief role focuses on browsing and map-oriented views. Relief users can open report lists and inspect report details, but they do not change report status in this prototype. That separation avoids conflicting status changes and keeps the verification decision inside the administrator workflow.

\FloatBarrier
\subsection{Administrator Dashboard Features}

The web dashboard is used for report review and user management. After login, it loads the current profile and blocks routes that require administrator access. Administrators can list incoming reports, filter by status, inspect evidence thumbnails, and update status values such as \texttt{pending}, \texttt{verified}, \texttt{resolved}, and \texttt{rejected}. Status changes are sent to the gateway and forwarded to the reports service through RabbitMQ so the database and cache remain consistent.

\section{Deployment and Release Automation}

The prototype runtime is containerized to keep local and deployed environments consistent. Docker Compose is used for local development to start all dependencies (RabbitMQ and Redis) alongside the backend services \cite{dockerComposeDocs}. Deployment is handled using a simple container-based approach: images are built and published, and Azure App Service is configured to run the latest images with environment configuration provided by the platform \cite{azureAppServiceContainersDocs}.

Automation is implemented with GitHub Actions to build images, push them to a registry, and update the deployment configuration \cite{githubActionsDocs}. This reduces manual steps and matches continuous delivery practice, where build and deploy logic is kept in version-controlled pipelines \cite{humble2010continuousDelivery,kim2016devopsHandbook}.

\section{Result Summary}

At the end of implementation, VietFlood can be run locally using Docker Compose and exercised through the mobile and web clients. The backend exposes REST endpoints for authentication and report management through the API gateway. A full endpoint list is summarized in Appendix~A (Table~\ref{tab:appendix-api-endpoints}), including representative response samples used in the evaluation.

The system demonstrates the intended role split in practice: citizens submit reports, relief users browse location-aware views, and administrators review and update report status. These results are evaluated in Chapter~5 through scenario walkthroughs and functional test checklists.
